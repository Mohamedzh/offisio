### High-level how-to (when approved, in this order)

1. **Generated listings batch.** One script (`scripts/generate-units.ts`): per unit, fix a room brief (district, kind, desks, light), generate 4–6 photorealistic frames with `muse-image-1.0` varying only camera position, assemble a 2 s/frame slideshow mp4 with ffmpeg, upload via the existing Blob path, then run the existing upload pipeline (specs → listing) so titles/prices match the unit. Seed 5–7 units: Zamalek, Heliopolis, Maadi (2nd angle), New Cairo, Nasr City, Alexandria Chatby, Alexandria Louran. Acceptance: each unit page 200, all media Blob 200, spec line + varied price/district on home cards, titles contain the right rent.
2. **Paymob test-card run.** On a daily-bookable unit: book a day in chat, check out with the dashboard test card (success), confirm booking only after webhook; repeat with a declined card and confirm the booking stays unconfirmed. Record both outcomes here. No code expected; fix only if the run exposes a gap.
3. **Location pin + nearby cafes step.** First give each unit a location: seed/demo units get district-centroid coords labelled approximate; the upload form gains an optional "paste a Google Maps link" field parsed to lat/lng (no schema change if stored with the listing data; a `units.lat/lng` migration only with owner approval). Unit page shows "Open in Maps" (exact pin when present, district otherwise, always labelled). Then `lib/pipeline/nearby.ts` (idempotent, re-runnable, `POST /api/units/[slug]/nearby`): query OpenStreetMap Overpass for `cafe|restaurant` within ~1.2 km of the pin, cache the 1–2 nearest named places, fall back to the curated per-district list in `lib/addons/catalog.ts` when Overpass fails; menu items/prices come from the curated catalog matched by place type, never invented. Surface "Near this office" on the unit page and let chat add-ons use the unit's cafes. Acceptance: every seeded unit has a maps link and 1–2 nearby cafes whose items can be added to a booking; Overpass failure still yields the curated fallback.
4. **QStash-driven simulated order status.** Approved 2026-10-28, env vars in place: on cafe-order creation, publish delayed QStash messages that call back a signed endpoint advancing `cafe_status` (sent_to_cafe → confirmed → delivered); verify QStash signatures (`QSTASH_CURRENT_SIGNING_KEY`/`QSTASH_NEXT_SIGNING_KEY`) on the receiver; booking page shows the timeline labelled as simulation, with the real WhatsApp send underneath. In-app advance remains the fallback. Acceptance: a booking with cafe items visibly progresses to delivered without manual DB edits, and a tampered callback is rejected.

Out of scope for this expansion: photo-based geolocation, real browser/computer-use ordering, a standalone microservice, WhatsApp location capture (deferred, see table), and presenting generated units as filmed real offices.
