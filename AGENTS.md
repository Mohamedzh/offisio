# AGENTS.md — Offisio

Instructions for coding agents working in this repository. The Next.js block above is tooling-generated; everything below is project rules and wins on product/stack decisions.

## Project

Offisio — office listing and booking agent for the Meta Global AI Developer Hackathon (Indie track, solo). An owner uploads a short video of an office; the app produces specs, a bilingual Arabic/English listing, and restaged photos (furniture removed, then restyled). Renters book by chatting in Egyptian Arabic.

Read [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) before structural changes, then [docs/DESIGN.md](docs/DESIGN.md). If a change contradicts either, update the doc in the same commit and say why.

## Hard rules (no exceptions)

1. **Meta models only in the product's AI.** Every model call in the app goes to the Meta Model API (`https://api.meta.ai/v1`). Never add another AI provider or SDK to a request path.
2. **New work only.** Do not copy code, data or assets from other projects. Generate everything fresh in this repo. *One owner-approved exception (2026-10-31):* demo menu data for ~150 chain brands, collected once (not a live scraper) from public listings on elmenus.com. It is labelled everywhere it shows ("Menu source: elmenus.com (demo data, not affiliated)"); production would use an authorized integration. Never claim elmenus as a partner or contributor.
3. **Only licensed assets.** No stock images, furniture photos or fonts we don't have rights to. Use our own footage (owner-shot walkthroughs, stored on Vercel Blob; local copies in the gitignored `/public/demo`) or images generated by `muse-image-1.0`.
4. **No secrets in the repo.** API keys live in environment variables only (`META_API_KEY`, `DATABASE_URL`, `DATABASE_URL_POOLED`, `BLOB_READ_WRITE_TOKEN`, `XPAY_SECRET_KEY`, `XPAY_WEBHOOK_SECRET`; the full list is in [.env.example](.env.example)). The repo is public.
5. **Small commits.** One logical change per commit, with a clear message. The history is our evidence of work done during the hackathon.

## Model routing and PII (read before touching any AI handler)

| Data class | Examples | Allowed model | Why |
|---|---|---|---|
| Public / synthetic | Test prompts, fake units, demo footage we shot, style prompts | `muse-spark-1.3` or `muse-spark-1.3-contributor` | Contributor is cheaper for iteration; content may train Meta models, so nothing private may ever go here |
| Product data, no PII | Keyframes of empty/furnished rooms, specs JSON, listing copy, style prompts | `muse-spark-1.3`, `muse-image-1.0` (`sam-3.1` dropped 2026-10-27: no callable endpoint, see [docs/plan/01](docs/plan/01-capability-tests.md)) | Normal product path |
| PII | Renter name, phone, chat transcripts, voice notes, owner contact details | `muse-spark-1.3` only; voice-note audio may also go to `muse-voice-transcribe-1.0` (not a contributor model). **Never** `muse-spark-1.3-contributor` | Contributor content may be used for training; PII must never be routed there |

Enforcement, not convention:

- Model IDs and prompts live only in `lib/meta/`. The client exposes `meta.public` (may use contributor), `meta.nonPii` (spark; contributor only via the local dev switch) and `meta.product` (never contributor). No other code picks a model ID.
- Any handler that receives chat text, a phone number, a name, or audio must use `meta.product`. When in doubt, treat data as PII.
- Dev switch ([06](docs/plan/06-judge-ready.md) 6.3): `OFFISIO_DEV_MODELS=modal` (preferred) sends **non-PII** calls (survey, specs, listing) to our own **Muse Spark Open** deployment on Modal (`MODAL_SPARK_URL`, `MODAL_KEY`, `MODAL_SECRET`; open-weight Meta model, Modal credits until Nov 4). `=contributor` uses `muse-spark-1.3-contributor` instead. Only for local runs on our own or synthetic footage. Ignored whenever `VERCEL` is set, so production always uses `muse-spark-1.3`, and chat never switches. Seeded/demo data is generated on `muse-spark-1.3`.
- Any model output that feeds code must be structured (JSON schema) and validated before use.
- If unsure whether an API supports something (masks on edits, video segmentation parameters), write a minimal test in `scripts/` and run it before building on it. See the unknown-capability list in [docs/DESIGN.md](docs/DESIGN.md).

## Scope

In scope: the demo loop (upload → specs → listing → removal/restaging → chat booking), plus these owner-approved additions:
- payments in **XPay test mode only** (booking confirms on a signed webhook);
- owner sign-in with **Clerk** (Google), with renters staying guests (stretch, [06](docs/plan/06-judge-ready.md) 6.9; cut if time runs out);
- a **required** per-unit location (`units.lat/lng`) and "near X" search for the agent (planned, 6.7);
- nearby cafes/restaurants per unit via the **Google Places API**, matched to a chain-brand menu catalogue (one-off demo import, see rule 2) or read from an owner's menu photo by Muse; long post-upload steps chained with **QStash** (planned, 6.7, owner decision 2026-10-31);
- curated cafe add-ons with a WhatsApp order link (built); menu items become add-ons for **daily** bookings;
- **renter booking over WhatsApp** via the Meta WhatsApp Cloud API (owner's own number), same agent and tools, XPay test-mode payment links (planned, 6.8).

Out of scope: live payments, cash on delivery, partial payments, standalone food orders, accounts beyond owner sign-in, reviews, map search UI, host analytics, mobile apps, a separate backend service, live scraping of any third-party site. Parked: QStash order status (06 O6). Don't build these, even partially.

When a task grows, propose the smallest version that still demos well instead of expanding it.

## Stack and conventions

- Next.js 16 (App Router), TypeScript strict, Tailwind 4, pnpm. Postgres on Neon, Vercel Blob for media, deployed on Vercel.
- Server work in route handlers under `app/api`; pipeline steps in `lib/pipeline`, each one independently re-runnable; booking agent in `lib/agent`; DB in `lib/db`.
- Bilingual UI: English (LTR) is the default locale (owner decision 2026-10-27, kept for judges), with a full Arabic (RTL) variant of every page under `/ar`. Test both `dir="rtl"` and `dir="ltr"` layouts. Use logical CSS properties (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`) so layouts mirror correctly.
- Keep functions small; no new dependencies without a reason in the commit message. Ask before adding a dependency, changing the stack, or adding scope.

## Agent team and cost discipline

One frontier-model architect (this session) plans; cheaper agents implement. Do not burn frontier tokens on bulk code writing.

Role definitions live in [docs/agents/](docs/agents/README.md); spawn from those files verbatim.

| Role | Model | Gets | Must return |
|---|---|---|---|
| Architect / planner (main session) | `muse-wonder-1.0` | Goal, docs, checkpoints | Segment brief: exact files, interfaces, acceptance tests, stop conditions |
| Implementor | `muse-spark-1.3-contributor` | One segment brief, named files only | Diff + commands run + failures, no scope expansion |
| Test writer & runner | `muse-spark-1.3-contributor` | Segment brief + acceptance list | Jest/Vitest tests that fail before and pass after, run output |
| Reviewer | `muse-spark-1.3-contributor` | Diff + brief | Findings by severity; approves or sends back, never rewrites silently |
| QA integrity | `muse-spark-1.3-contributor` | Pipeline/API surface + synthetic fixtures | Pass/fail per check with evidence; gaps named |
| QA UI | `muse-spark-1.3-contributor` | Running app URL + scripted flows | Pass/fail per flow (AR RTL + EN LTR) with evidence |
| QA head reviewer | `muse-wonder-1.0` | Full diff + all QA evidence | Ship / fix-first verdict; manual call or very large/complex features only |

Rules: briefs are self-contained (a fresh agent with no session history must succeed from the brief + linked docs alone). One segment per subagent. The architect reviews diffs, never re-derives them from memory. Contributor agents never touch real PII (names, phones, transcripts, voice notes) — escalate those tasks to `muse-spark-1.3` or Wonder. Full detail: [docs/plan/README.md](docs/plan/README.md).

## Working in segments (avoid long sessions)

Work is split into segment files under [docs/plan/](docs/plan/README.md), indexed by [docs/PLAN.md](docs/PLAN.md). Start a fresh chat session per segment; long sessions burn tokens and lose detail.

At every session start: read this file, [docs/PLAN.md](docs/PLAN.md), and the active segment file — nothing else unless the segment names it. At every session end: update the segment file (status, decisions, next step) and [docs/PLAN.md](docs/PLAN.md) in the same commit. If a session is growing past one segment, stop, write the handoff into the segment file, and start fresh.
